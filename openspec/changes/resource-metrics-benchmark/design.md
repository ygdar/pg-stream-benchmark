## Context

Проект — бенчмарк относительной скорости вставки TSV в PostgreSQL (первая итерация: 5 стратегий по времени). Эта итерация расширяет измеряемость: помимо времени добавляются расход памяти клиента, утилизация CPU клиента и сервера, соотношение полезного трафика к накладным расходам. Окружение — Windows, PG в Docker через loopback; абсолютные числа не цель, важна относительная картина по стратегиям.

## Goals / Non-Goals

**Goals:**
- Для каждой стратегии × размер собирать: пиковая память клиента, средняя/пиковая CPU клиента, CPU сервера (оценочно), payload/overhead ratio.
- Все новые замеры — вне тайминга `@Benchmark`, чтобы не искажать существующее время.
- Минимум новых зависимостей; использовать штатные средства (.NET, PostgreSQL pg_stat_*).

**Non-Goals:**
- Точный абсолютный замер сетевого трафика на loopback (через связки пакеты/npgsql) — только оценочный payload/overhead по проводному механизму.
- Переделка существующих пяти стратегий и временного тайминга.
- Сбор метрик на распределённом/прод-окружении (локальный Docker-loopback).

## Decisions

### D1: Сбор клиентских метрик через System.Diagnostics
`Process` текущего процесса: `WorkingSet64` (пик), `TotalProcessorTime`/`ProcessorTime` (CPU). Пик памяти — сэмплирование в фоне во время загрузки; CPU — это `Process.GetCurrentProcess().TotalProcessorTime` до/после (дельта), нормированное на время прогона и число ядер.
*Обоснование:* встроено в .NET, минимум зависимостей, не требует прав на Windows.
*Альтернатива:* PerformanceCounter — отклонено (чувствительно к правам, лишняя зависимость).

### D2: Серверный CPU через pg_stat
Опрос `pg_stat_database`/`pg_stat_activity` или просчёт времени по `pg_stat_bgwriter`/блуждающие сэмплы `pg_stat_activity.state` вокруг прогона; CPU сервера оценивается из дельты `blk_*/tup_*`-работы и системных счётчиков. Практично: `pg_stat_database` даёт активность БД, а доля CPU — оценочно через относительный вклад прогона на фоне idle.
*Обоснование:* не требует внешнего мониторинга; значения оценочные.
*Альтернатива:* внешний `pg_top`/`psutil`-агент — отклонено: лишние зависимости, сложнее воспроизводимо.

### D3: Оценка payload/overhead по проводному механизму
Полезный объём = детерминированный размер строк (файл TSV). Накладные = лишние байты каждого механизма:
- **Batch (multi-row VALUES)**: текстовые параметры SQL + разделители + команда; overhead ≈ служебные байты батча;
- **Binary COPY (raw и LINQ2DB)**: бинарные маркеры колонок/длины, типовые заголовки;
- **Server-side COPY (native)**: почти нулевой клиент-серверный обмен данными (данные не идут через клиента) — ratio высокий/^∞.
Формула: `ratio = payloadBytes / (payloadBytes + overheadBytes)`.
*Обоснование:* относительное сравнение механизмов по «чистоте» передачи; точный packet-level трафик на loopback не нужен.
*Альтернатива:* сниффер сетевого трафика (Wireshark/ETW) — отклонено: тяжёлое, не детерминированное.

### D4: Метрики вне тайминга
Сбор памяти/CPU запускается до `@Benchmark`, останавливается после; в сам замер времени ничего нового не включается. Итоговый отчёт объединяет время + ресурсы.
*Обоснование:* сохраняет честность временного сравнения; метрики агрегируются по прогону.

### D5: Единый отчёт-сводка
После прогона формируется один общий файл-сводка (напр. `summary.csv`/`summary.md`) по всем запущенным бенчмаркам текущего прогона. Источник — агрегированные результаты существующих отчётов (`BenchmarkDotNet.Artifacts/results/*-report.csv`): время + клиентские метрики + серверная CPU + payload/overhead. Файл перезаписывается на каждый прогон, объединяя все стратегии × размеры.
*Обоснование:* единая таблица для сравнения стратегий без ручного сведения CSV. 
*Альтернатива:* оставить только пер-бенчмарк отчёты — отклонено: сводка удобнее для чтения сравнительных результатов.

## Risks / Trade-offs

- **[Серверный CPU на loopback неточен]** → Фиксируются как оценочные относительные значения; основной сигнал — разница между механизмами, а не число.
- **[Payload/overhead — модель, не факт]** → Модель построена на проводном механизме и детерминированном размере данных; документируется как оценка.
- **[Пик памяти клиента зависит от GC]** → Используем пиковый WorkingSet как верхнюю границу, указываем метод измерения.
- **[Оверhead-замеры добавляют время]** → Метрики собираются отдельным потоком/до-после, не входят в `@Benchmark`, поэтому тайминг не меняется.

## Migration Plan

- Добавить модуль метрик (клиентские + серверные + payload/overhead) и расширить отчёт.
- Прогнать validation для проверки работы метрик, затем dev; full по необходимости/времени.
- Откат: выключение сбора метрик флагом — без изменения существующих стратегий.
