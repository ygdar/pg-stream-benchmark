## Why

Первая итерация замеряла только **относительное время** вставки пяти стратегий. Для выбора стратегии в проде важен не только тайминг: значимы расход памяти на клиенте (файл может не помещаться в RAM), утилизация CPU на клиенте и сервере (стоимость инфраструктуры), а также "гигиена" сетевого обмена — сколько полезных данных уходит против накладных расходов на каждый проводной механизм. Эти метрики позволяют выбрать стратегию не только «быструю», но и «дёшевую по ресурсам».

## What Changes

- К существующему замеру времени добавляются сопутствующие метрики для каждого прогона стратегии:
  - **Расход памяти на клиенте** — пиковое значение managed/working set процесса-клиента за прогон;
  - **Нагрузка CPU на клиенте** — средняя/пиковая утилизация одного ядра процесса-клиента во время вставки;
  - **Нагрузка CPU на сервере** — утилизация CPU процесса PostgreSQL во время прогона;
  - **Соотношение полезного трафика к накладным расходам (ratio payload / overhead)** — для каждого проводного механизма: сколько байт полезных данных строк против суммарного сетевого объёма (непустые строки + команды/фреймы/пакеты) между клиентом и сервером.
- Метрики снимаются **вне тайминга** (отдельно от `@Benchmark`), чтобы не искажать время — как и прочий setup/teardown.
- Источник фактов для «полезного трафика» — тот же сгенерированный TSV-файл (байты полезных данных известны детерминированно).
- Результат — расширенный отчёт: для каждой стратеги × размер — время + память + CPU (client/server) + payload/overhead ratio.
- **Единый отчёт-сводка**: в дополнение к отдельным отчётам по каждому бенчмарку генерируется один общий файл-сводка по всем запущенным бенчмаркам текущего прогона, объединяющий время и ресурсные метрики всех стратегий × размеров.
- Новая capability и набор утилит метрик; benchmark-классы прежних пяти стратегий не меняются функционально, обогащаются измерениями.

## Capabilities

### New Capabilities
- `resource-metrics`: Замер расхода памяти клиента, утилизации CPU клиента и сервера PostgreSQL, а также соотношения полезного трафика к накладным расходам при обмене клиент-сервер для каждой стратегии вставки.
- `summary-report`: Формирование единого отчёта-сводки по всем запущенным бенчмаркам текущего прогона в одном файле (объединяет время и ресурсные метрики всех стратегий × размеров).

## Impact

- **Код**: новые модули измерения ресурсов (клиентская память/CPU, серверный CPU через pg_stat_activity/`pg_stat_database`, учёт сетевого трафика) + расширение отчётности + генератор общего отчёта-сводки. Benchmark-классы получают дополнительные метрики, тайминг не затрагивается.
- **Зависимости**: `System.Diagnostics.Process` (клиентская память/CPU) — встроено; серверный CPU — SQL-запросы к PostgreSQL (pg_stat_*); трафик — оценка по числу строк×размер ряда и известной длине сетевых фреймов/команд.
- **Системы**: прежнее окружение (локальный PG в Docker). Накладные расчёты трафика опираются на проводной механизм каждой стратегии.
- **Точность**: нагрузка CPU сервера и сетевой трафик измеряются оценочно (Docker-loopback), фиксируются как относительные, а не абсолютные значения.
