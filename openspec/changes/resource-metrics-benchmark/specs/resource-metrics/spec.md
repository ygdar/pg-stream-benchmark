## ADDED Requirements

### Requirement: Расход памяти на клиенте
Бенчмарк SHALL для каждого прогона каждой стратегии фиксировать расход памяти на клиенте (пиковое значение рабочего набора процесса-клиента за прогон). Замер SHALL выполняться штатными средствами `System.Diagnostics.Process` и фиксироваться для каждого прогона.

#### Scenario: Измерение пиковой памяти
- **WHEN** стратегия выполняет загрузку данных
- **THEN** фиксируется пиковое значение памяти процесса-клиента за время прогона

#### Scenario: Память вне тайминга
- **WHEN** производится замер времени стратегии
- **THEN** замер памяти не добавляется к замеренному времени и не искажает его

### Requirement: Нагрузка CPU на клиенте
Бенчмарк SHALL фиксировать утилизацию CPU процесса-клиента (среднюю и пиковую за прогон) для каждой стратегии. Клиентский CPU-замер SHALL использовать процессные счётчики `Process.CpuTime`/`ProcessorTime`.

#### Scenario: CPU клиента замерен
- **WHEN** стратегия загружает данные
- **THEN** собирается выборка утилизации CPU процесса-клиента и вычисляются средние/пиковые значения

#### Scenario: Клиентский CPU вне тайминга
- **WHEN** измеряется время загрузки
- **THEN** клиентский CPU-замер не входит в измеренное время

### Requirement: Нагрузка CPU на сервере
Бенчмарк SHALL фиксировать утилизацию CPU процесса PostgreSQL (сервера) во время каждого прогона стратегии через системные представления PostgreSQL. Значения SHALL считаться оценочными (относительными), а не абсолютными.

#### Scenario: Серверный CPU замерен
- **WHEN** стратегия выполняет загрузку
- **THEN** из PostgreSQL собирается утилизация CPU серверного процесса за время прогона

#### Scenario: Оценочность серверного CPU
- **WHEN** CPU сервера отображается в отчёте
- **THEN** он помечается как оценочное относительное значение, а не точное абсолютное

### Requirement: Соотношение полезного трафика к накладным расходам
Бенчмарк SHALL для каждой стратегии оценивать объём полезного трафика (байты полезных данных строк) и суммарный накладной обмен между клиентом и сервером и вычислять отношение payload к overhead. Оценка SHALL опираться на проводной механизм стратегии (multi-row VALUES, binary COPY, server-side COPY) и детерминированный размер полезных данных.

#### Scenario: Полезный объём по механизму
- **WHEN** вычисляется полезный трафик стратегии
- **THEN** он выводится из размера полезных данных (строк файла) без учёта сетевых накладных

#### Scenario: Накладные по механизму
- **WHEN** вычисляется overhead стратегии
- **THEN** учитываются лишние байты, вносимые проводным механизмом (служебные команды, разделители, батчинг) относительно полезных данных

#### Scenario: Отчёт с соотношением
- **WHEN** формируется отчёт прогона
- **THEN** для каждой стратегии присутствует значение payload/overhead ratio
