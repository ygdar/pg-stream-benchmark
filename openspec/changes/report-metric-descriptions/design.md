## Context

Отчёт-сводка формируется в `benchmark/Metrics/SummaryReport.cs`: читает тайминг из BDN `*-report.csv`, объединяет с ресурсными метриками из `MetricsStore` (JSON-файлы по ключу «стратегия × размер») и пишет `summary.csv` + `summary.md`. Источники метрик — `ResourceMetrics` (клиентская память/CPU через `Process`, серверная «активность» через `pg_stat_database`) и `TrafficModel` (детерминированная оценка payload/overhead по размеру TSV-файла и проводному механизму). Сейчас в сводке нет пояснений метрик, а payload/overhead выводятся в сырых байтах.

## Goals / Non-Goals

**Goals:**
- В `summary.md` добавить читаемую легенду, где для каждой метрики указано: что измеряет, как получена, в чём выражается.
- Выводить полезные данные и накладные в человекочитаемых единицах (МБ, при больших объёмах — ГБ).
- Сохранить прежний состав/порядок строк таблицы, не ломая тайминг и сами замеры.

**Non-Goals:**
- Не менять процесс измерения метрик (память/CPU/серверная активность/трафик остаются как есть).
- Не менять JSON-схему метрик в `benchmark-data/metrics/*.json`.
- Не вводить новые метрики; только документировать и переформатировать существующие.

## Decisions

### D1: Легенда метрик как отдельный раздел в `summary.md`
В конец `summary.md` добавляется раздел «О метриках», где построчно (или списком) описывается каждая колонка таблицы. Описание строится по фиксированной структуре: **Что измеряет (суть)** + **Как получено (источник)** + **В чём выражается (единицы)**. Это минимально инвазивно: таблица не меняется структурно, пояснения просто документируют колонки.
*Альтернативы:* вставлять пояснение в заголовок каждой колонки — отклонено: раздувает таблицу и плохо читается; выносить в отдельный файл — отклонено: теряется связь с отчётом.

### D2: Единицы payload/overhead — МБ, а при ≥1 ГБ — ГБ
Вводится хелпер форматирования размера: значение в байтах форматируется в МБ с точностью (напр. `76.0 МБ`), а при `bytes >= 1024^3` (1 ГБ) — в ГБ с точностью (напр. `1.6 ГБ`). Колонки «Полезные данные» и «Накладные» в `summary.csv` и `summary.md` используют этот формат; их заголовки меняются с «, байт» на «, МБ/ГБ».
*Альтернативы:* оставить байты → противоречит требованию; динамически подбирать единицу внутри ячейки (КБ/МБ/ГБ) — отклонено: пользователь явно просил МБ/ГБ с ростом до ГБ.

### D3: Единый источник описаний в коде
Список описаний метрик держится рядом с формированием строк в `SummaryReport` (массив/словарь «заголовок → описание»), чтобы CSV и MD генерировались из одного источника и не расходились.
*Альтернативы:* хардкодить отдельно в каждой ветке вывода — отклонено: риск рассинхрона и дублирования.

## Risks / Trade-offs

- **[Легенда не синхронизирована с фактическими колонками]** → Описания строятся из того же списка колонок, что и шапка таблицы (D3), в верификации проверяется совпадение.
- **[Смена единиц (байт→МБ/ГБ) сломает парсинг консьюмерами CSV]** → Это осознанный BREAKING по требованию; `summary.csv` обновляется согласованно с `summary.md`; формат документируется в легенде.
- **[Округление скроет мелкие различия payload]** → Точность МБ/ГБ достаточно для цели (сравнение стратегий × размеров); при необходимости оставляется один десятичный знак.

## Migration Plan

Изменение локально: правки `SummaryReport.cs`, повторная сборка (Release), прогон validation и dev для NativeCopy, проверка `summary.md`. Откат — предыдущие форматы/без легенды из VCS.

## Open Questions

- Нужно ли выводить и минимальную точность для ГБ (сколько знаков)? По умолчанию — один знак после запятой для МБ и ГБ.
- Стоит ли добавить колонку описания прямо в CSV-заголовок? По умолчанию — нет, легенда только в MD (CSV остаётся машинно-читаемым).
