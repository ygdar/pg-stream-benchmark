## Context

Проект — бенчмарк скорости вставки TSV в PostgreSQL (BenchmarkDotNet, .NET 9). Набор из пяти стратегий A–E регистрируется в `Program.cs` и оборачивается `BenchmarkSwitcher`; метрики (тайминг, ресурсы, сводка) раскладываются по кодам стратегий через маппинги в `Metrics/ResourceMetrics.cs` и `Metrics/SummaryReport.cs`. Стратегия D (`EfChunk`) — единственное место, использующее EF Core (класс `BenchDbContext`, пачки `SaveChanges`). На медиум/больших объёмах она на порядок медленнее остальных и растягивает каждый полный прогон.

## Goals / Non-Goals

**Goals:**
- Полностью исключить стратегию D (EfChunk) из запускаемого набора, из маппингов метрик и из данных прогонов.
- Сократить общую длительность полных/разработочных прогонов.
- Оставить набор самосогласованным: 4 стратегии A, B, C, E без «мёртвых» ссылок.

**Non-Goals:**
- Не менять поведение оставшихся стратегий (тайминг, ресурсные метрики, формат отчётов).
- Не рефакторить механизм запуска (`BenchmarkSwitcher`) и не менять схему нейминга стратегий A/B/C/E.

## Decisions

### D1: Полное удаление модуля EfChunk, а не отключение
Удаляются класс `EfChunkStrategy` и `BenchDbContext` (`DataAccess/EfChunkStrategy.cs`), класс `EfChunkBenchmark` (`Benchmarking/InsertBenchmarks.cs`) и его регистрация в массиве `benchmarkTypes` (`Program.cs`). Не скрываем через фильтр — убираем из кода, чтобы набор не разрастался и не появлялись ложные «5 стратегий».
*Альтернативы:* оставить файл, но исключить из запуска фильтром — отклонено: оставляет мёртвый код и риск случайного включения в будущем.

### D2: Синхронная чистка маппингов метрик
Везде, где стратегия D фигурирует как особая сущность, удаляется её запись:
- `ResourceMetrics.TrafficModel.MechanismFor` — убирается ветка `"D_EfChunk" => "SQL row-batch"`; ветка `else` теперь описывает только `multi-row VALUES` (её реализует A).
- `SummaryReport.StrategyMap` — убирается кортеж `("EfChunk", "D_EfChunk")`.
- `SummaryReport.StrategyRu` — убирается запись `["D_EfChunk"]`.
Логика остальных стратегий (B/C — binary COPY, E — server-side COPY) не меняется.
*Альтернативы:* оставить маппинги «на будущее» — отклонено: мёртвые ветки не тестируются и искажают трафик-модель.

### D3: Удаление устаревших файлов данных
Удаляются `benchmark-data/metrics/D_EfChunk-1000.json`, `-10000.json`, `-1000000.json`, `-2000000.json`. Данные прошлых прогонов стратегии D в проде более не нужны; сводный отчёт формируется из текущего прогона.
*Альтернативы:* архивировать данные — отклонено: нет требования хранить историю; исходники TSV остаются единственным источником воспроизводимости.

### D4: Приведение зависимостей EF Core
Из `DbBenchmark.csproj` при удалении единственного пользователя EF удаляются пакеты `Microsoft.EntityFrameworkCore` и `Npgsql.EntityFrameworkCore.PostgreSQL`, если поиск по исходникам не выявит других использований EF. Перед удалением (во время реализации) выполняется проверка `grep -r "EntityFramework\|Npgsql.EntityFrameworkCore" benchmark/` — если найдены иные использования, пакеты сохраняются, а задача помечается примечанием.
*Альтернативы:* оставить зависимости «на всякий случай» — допустимо как минимальный шаг, но цели чище их удалить.

### D5: Правка текстовых упоминаний о количестве стратегий
Комментарии и подписи, ссылающиеся на «5 стратегий» / «EF chunk» в `Program.cs` (и при необходимости `README.md`), приводятся к актуальному набору (4 стратегии: A, B, C, E). Это не меняет логику, только уменьшает вводящие в заблуждение описания.

## Risks / Trade-offs

- **[Где-то ещё используется EF Core / BenchDbContext]** → Прямое удаление пакетов сломает сборку; перед удалением выполняется поиск использования; при конфликте пакеты сохраняются, удаляется только стратегия D.
- **[Сводка/отчёт упадут на отсутствии данных D]** → Отчёт строится только по запущенным бенчмаркам текущего прогона; удаление данных D не затрагивает генерацию сводки, проверяется в верификации.
- **[Опечатка в маппингах при чистке сломает A/B/C/E]** → Правки минимальны и точечны; верификационный прогон в validation-режиме подтверждает, что оставшиеся стратегии всё ещё отчитываются.
- **[Забытое упоминание «5 стратегий»]** → Задача правок покрывает `Program.cs`/`README.md`; для полноты выполняется `grep -rni "efchunk\|5 стратег" benchmark/ README.md`.

## Migration Plan

Изменение аддитивно-удаляющее, без развёртывания. Шаги: удалить файлы стратегии → убрать регистрацию → почистить маппинги → удалить данные/пакеты → собрать и прогнать validation. Откат: возврат удалённых файлов и записей из истории VCS (git); специальная процедура отката не требуется.

## Open Questions

- Нужно ли чистить исторические ссылки на EfChunk в папках прежних изменений (`openspec/changes/*/`)? (По умолчанию — нет: это история решений; правится только текущий код/README.)
