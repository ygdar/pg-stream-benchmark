## Context

Вafka-проект greenfield: бенчмарк скорости вставки TSV в PostgreSQL. Цель — измерить **относительный** выигрыш по времени стратегий вставки, а не абсолютные значения. Окружение — рабочая станция на Windows, PostgreSQL последней версии в Docker, дефолтная конфигурация (durability по умолчанию, таблица не оптимизируется под бенчмарк).

## Goals / Non-Goals

**Goals:**
- Честное сравнение 5 стратегий вставки одного и того же TSV-файла.
- Модель данных — C# класс, общий для всех стеков.
- Воспроизводимость: детерминированная генерация, pinned-версия PG, фиксированный seed.
- Масштабируемость структуры: новые модели и стратегии добавляются новыми классами.
- Отдельный замер «шипучего» (механизм вставки) при общей стоимости парсинга.

**Non-Goals:**
- Абсолютные цифры производительности/пропускной способности.
- Тюнинг PostgreSQL (дефолтная конфигурация — осознанный выбор).
- Нагрузочный скрипт прода, ETL-конвейер как продакшен-продукт.
- Измерение in-memory вставки без чтения файла (опция, не в скоупе).

## Decisions

### D1: Единый .NET-проект с иерархией пакетов
Один csproj, внутри — папки: `Domain`, `Generation`, `Parsing`, `DataAccess`, `Benchmarking`. BenchmarkDotNet сам раскрывает кейсы по `[Params]`.
*Альтернативы:* multi-проектная структура Maven/Gradle-стиля — отклонено: избыточно для одного бенчмарка, усложняет запуск.

### D2: TSV-файл как единый источник истины
Все 5 стратегий читают один и тот же сгенерированный TSV. Общая стоимость (чтение + парс) вычитается при сравнении относительного выигрыша. Требование «файл не влезает в память» удовлетворяется потоковым чтением.
*Альтернативы:* генерация моделей в памяти — отклонено: не даёт #E (нативный COPY файла) и не моделирует реальный вход прод-задачи.

### D3: `InsertStrategy` — точка расширения
Интерфейс `load(stream)` инкапсулирует каждую стратегию. Новая модель меняет только `DataRecord` + маппинг колонок; новая стратегия — новый класс. Это ядро future-экспериментов.

### D4: Проводной механизм как главная ось сравнения
BINARY COPY (raw `copyIn` и LINQ2DB `BulkCopyType.ProviderSpecific`) — единый нативный протокол. A/D — SQL-батчинг. E — серверный COPY. Так сравниваются разные *механизмы*, а не эффективность ORM.

### D5: Парсинг через source-generated regex
`[GeneratedRegex]`-методы (предгенерированный конечный автомат) для разбора TSV-строк. CsvHelper используется **только** при генерации/сериализации.
*Обоснование:* минимум CPU-оверхеда, отдельная точка оптимизации.

### D6: Три режима запуска
validation (1K/10K строк) — мгновенная проверка работоспособности при разработке, dev (1M/2M) — быстрая проверка логики, full (5M/10M/30M) — отчёт. Переключение флага/аргументом в `Program.cs`, чтобы 25 кейсов (5×5) не растягивались на часы на каждом локальном прогоне.

### D7: Выравнивание транзакций (конфаундер контроля)
A–D внутри одной транзакции на загрузку. E — собственный режим (server-side COPY). Разница в fsync/транзакционности фиксируется как задокументированный конфаундер, не маскируется.

### D8: SQLite возможностей/валидация
Каждый прогон: count строк в таблице == count строк в файле (иначе «быстрый» результат = незагруженные данные). Нативные COPY требует прав суперпользователя / `pg_read_server_files` и файла внутри контейнера.

## Risks / Trade-offs

- **[Парс TSV доминирует по времени]** → Общая стоимость одинакова для всех, относительная разница остаётся про механизм; при необходимости добавляем in-memory-серию как отдельный замер.
- **[Windows/Docker-loopback ограничивает абсолют]** → Одинаковая «шина» для всех методов, относительность сохраняется; абсолютные числа не цель.
- **[LINQ2DB BulkCopy + npgsql несогласован]** → Верификация на этапе реализации (BulkCopyType.ProviderSpecific), отдельная задача перед интеграцией.
- **[Декартово произведение Params (25 кейсов)]** → Режимы dev/full + сдержанный конфиг harness (мало warmup/итераций).
- **[Нативный COPY требует прав/файла в контейнере]** → Volume для TSV в docker-compose, суперпользователь/`pg_read_server_files` в setup, вне тайминга.
- **[Source-generated regex и экранирование TSV]** → Генерацию держим совместимой с COPY-форматом (корректное экранирование), чтобы файл читался и regex-парсером, и нативным COPY.

## Migration Plan

Нет существующего кода — проект создаётся с нуля. Развёртывание: `docker-compose up -d` + запуск бенчмарка (dev/full). Откат неприменим.
